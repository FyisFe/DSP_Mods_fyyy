# DSP 星际物流 挂机稳态性能分析

## 范围与约束

- 只分析**星际物流**（`GalacticTransport` + `StationComponent` Remote 部分）
- 不考虑：本地无人机、UI/渲染、`RefreshTraffic`（航路/建拆时触发）
- 目标场景：10000+ 个物流塔挂机稳态，tick spike 不均匀

所有行号基于 `GameCode-latest/`。

---

## 一、挂机时 spike "不均匀" 的根源

### 结论

`StationComponent.DetermineFramingDispatchTime`（`StationComponent.cs:3249-3253`）的判定**只看 time，不看 station**，所有 10000 塔完全同相触发：

```csharp
if (priorityIndex == 1)          return time % 10L == 0L;
if (priorityIndex == 2 || 3)     return time % 30L == 0L;
else                             return time % 60L == 0L;  // priority 4,5,6
```

配合 `GalacticTransport.GameTick`（`GalacticTransport.cs:175-205`）的 6×N 嵌套，单 tick 实际工作量分布：

| tick 条件 | 命中的 priority 数 | 外层迭代次数（N=10000） |
|---|---|---|
| `t % 60 == 0` | **6**（全部） | **~60,000** ← 巨型 spike，每秒 1 次 |
| `t % 30 == 0` 非 60 | 3（1,2,3） | ~30,000 ← 中 spike，每半秒 1 次 |
| `t % 10 == 0` 非 30 | 1（priority 1） | ~10,000 ← 小 spike |
| 其余 54/60 | 0 | 0（只跑外层空循环）|

> 注：上表是**外层 for 迭代次数**（6×N）。真正的 `DetermineDispatch` 调用数受 `GalacticTransport.cs:195-200` 的 `routePriority` 分支门控——一塔每 `t%60` 帧最多调用 5 次（`Prioritize`）/ 4 次（`Only`/`Designated`）/ 1 次（`Ignore`），并非每次迭代都调用。量级不变，spike 的根因（全塔同相）不变。

这就是用户感知的"挂机 CPU 尖峰不平均"——每秒一次大冲击 + 每 0.5 秒一次中冲击，其余 90% 的 tick 几乎空闲。

## 二、每 tick 持续开销（基线）

`PlanetTransport.GameTick` → `StationComponent.InternalTickRemote`（`StationComponent.cs:1714-2150`）
**每 tick、每 stellar 塔都跑**（不受 DetermineFramingDispatchTime 门禁约束）。

### 2.1 Warper 扫描（`StationComponent.cs:1731-1744`）
```csharp
if (this.warperCount < this.warperMaxCount)
{
    lock (this.storage)
    for (int i = 0; i < this.storage.Length; ++i)
        if (this.storage[i].itemId == 1210 ...)
}
```
只要 warper 未满就每 tick 扫全部 storage 槽。10000 塔 × ~30-50 格 + 10000 次 `lock(storage)` 获取。

### 2.2 工作飞船物理循环（`1768-2150`）
- 每架 in-flight ship 每 tick：
  - 行 1776-1779：`Math.Sqrt` 重算 planetA↔planetB 的 `_trip`
  - 行 1988 有**距离节流**：`num23 ∈ {1, 10, 30}`，远距离飞船物理 1/30 tick 算一次（**代码已有的好设计**）
  - 但外层 for 仍然每 tick 遍历所有 ship，状态机判断不被节流
- 到达时（`1824-1825`）：
  ```csharp
  Array.Copy(workShipDatas, i+1, workShipDatas, i, workShipDatas.Length - i - 1);
  ```
  O(workShipCount) 挪元素填洞；同 tick 多船到达退化成 O(ships²)

### 2.3 `_trip` 在同 tick 内被多处重算
`astrosData[].uPos` 一帧内不变，但 `InternalTickRemote:1779` 和 `DetermineDispatch:3008` 都在各自现算。

### 2.4 `priorityLocks` 递减循环（每 tick 恒定基线）
`InternalTickRemote:2548-2562` 每 tick、每 stellar 塔遍历 `priorityLocks[]` 递减 `lockTick`。
长度 = `stationMaxItemKinds`（≈5，见 `130`）。10000 塔 → 每 tick ~5 万次字段读写，**恒定基线（非 spike）**。
它正是 §5 P0 相位分散后"单塔锁时序仍成立"的机制：锁写入值 = period（`3256-3279`），每 tick 减 1，正好撑到该塔下次同优先级调度。

## 三、`DetermineDispatch` 单次开销（`StationComponent.cs:2913-3247`）

- 用 `remotePairProcesses[priority]` 做环形游标，从上次位置扫 `remotePairs[]`
- 每扫一对：读 `priorityLocks[]` → `lock(this.storage)` 读 6 字段（`2973-2978`：max/count/inc/remoteSupplyCount/totalSupplyCount/itemId）→ 必要时 `lock(other.storage)` 读 2 字段 → 重算 trip（行 3008）
- 找到可派送就 break，否则把当前 priority 的 num12 对走完
- **坑**：`idleShipCount==0` 或 `energy<=6e6` 只是把 `flag1=false`（行 3013-3014）**跳过当前这对**，do-while 循环**仍继续扫下一对**——无能量/无闲船的塔每次 spike 帧仍然白跑完整个 pair 环

## 四、稀疏数组扫描（次要）

`GalacticTransport.cs:190-202` 内层 `for index = 1..stationCursor`，每次都要 `stationPool[index] != null && id > 0 && gid == index`。8000 活塔 × 10000 槽 → 每 `t%60==0` 帧 60000 次无效判断。

## 五、优化方案（P0–P3，不改语义）

### P0 — 相位分散（消除"不均匀 spike"）

保持每塔的**调度频率不变**，但**按 gid 错开相位**：每 tick 只处理 1/period 的塔。

替换 `GalacticTransport.cs:185-204` 为：
```csharp
for (int priorityIndex1 = 1; priorityIndex1 < 7; ++priorityIndex1)
{
    int priorityIndex2 = priorityIndex1 % 6;
    int period = (priorityIndex1 == 1) ? 10
               : (priorityIndex1 == 2 || priorityIndex1 == 3) ? 30
               : 60;
    int phase = (int)(time % period);

    for (int index = 1 + phase; index < this.stationCursor; index += period)
    {
        var sc = this.stationPool[index];
        if (sc == null || sc.id <= 0 || sc.gid != index) continue;
        // …原三个 priority/routePriority 分支不变
    }
}
```

- 每塔每 period tick 仍然被调度 1 次（吞吐不变）
- 每 tick 外层负载：`N/10 + 2·N/30 + 3·N/60 = 13N/60 ≈ 0.217N`（约 **2170** 次 / 10000 塔，原文 1700 偏低）
- **削峰**：峰值从 `t%60` 的 6N 外层迭代降到恒定 ~0.217N，峰值 **-96%**（所以"-80% 以上"成立、且偏保守）
- **语义注意（修正）**：单线程不变，且**单塔自身**的锁时序保留（锁存活 = period = 该塔重访间隔，见 §2.4）。但**跨塔竞争**会变——原版竞争同一 demander 的多个 supplier 在同一帧按 gid 顺序解析，相位分散后落在不同 tick，"谁抢到这单"的胜负顺序改变。对挂机稳态吞吐无影响（货照走、甚至更公平），但**不是逐帧确定性等价**，多人/录像回放场景需评估。

### P1 — 热路径缓存

#### ① Warper 槽索引缓存
`StationComponent` 加 `int _warperStorageIndex = -1`，在 storage 配置变更处（少数几处）维护。
`InternalTickRemote:1731-1744` 的扫描改为直接查索引。
**收益**：10000 塔每 tick 省 ~50 万次字段比较 + 10000 次 lock。

#### ② `SupplyDemandPair.trip` 字段缓存
`RematchRemotePairs` 构建 pair 时就写 `pair.trip = planetDistance + r1 + r2`。
`DetermineDispatch:3008` 改为 `double trip = local1.trip`。
行星公转使距离慢变，可以每 N 秒刷一次或在 `GalacticTransport.GameTick` 开头批量更新。

#### ③ planet-pair 距离表（可选）
在 `PlanetTransport.GameTick` 开头基于 `astrosData[].uPos` 预算本帧距离表。
`InternalTickRemote:1779` 和 ②没覆盖的地方查表。

### P2 — 活跃塔列表

`GalacticTransport` 维护 `List<int> activeStellarStationGids`（Add/Remove 时更新）。
GameTick 改为遍历该列表，省掉 null/id/gid 三重校验。和 P0 的相位分散天然叠加（`for gid in activeList where gid % period == phase`）。

### P3 — 飞船到达 `Array.Copy` 换尾换法

`StationComponent.cs:1824-1825` 改为把末尾元素交换到 i 位置，从 O(workShipCount) 变 O(1)。
前提：先 grep 确认 `workShipDatas` 顺序没有外部语义依赖。

### P4 — 事件/脏标记驱动调度（天花板最高，风险也最高）

P0–P3 都是"把同样的浪费摊平/减常数"。**更根本的解法是消除浪费本身**：

稳态下绝大多数 `DetermineDispatch` 扫完整个 pair 环却派不出任何船（供给没到阈值 / 无闲船 / 需求已满）。轮询模型不管有没有事都付 O(pairs)。改为**只在"可能促成派送的状态变化"发生时**把该塔入队：
- storage 某槽 `count` 越过供给阈值
- 有船回到 idle（`InternalTickRemote:1827` `++idleShipCount` 处）
- `energy` 回升过 `6e6`

`GalacticTransport` 维护一个 dirty 队列，`GameTick` 只处理队列内的塔。**真正饱和/空闲的塔 → 趋近 0 开销**。

- 收益上限远高于 P0（P0 只摊平，P4 直接砍掉空转）
- 代价：大改、改变逐帧时序、需小心漏触发（漏一个事件 = 货卡住）。建议在 P0/P1 落地、性能仍不够时再上，且要充分回归测试。

### 实现合并建议

- **P1②③ 是同一件事**：`astrosData[].uPos` 一帧内不变。在 `PlanetTransport.GameTick` / `GalacticTransport.GameTick` 开头做**一次** uPos 快照（或直接缓存 `pair.trip`），`1779` 和 `3008` 共用一张表，不必拆两处实现。
- **P1① 可用脏标记替代索引缓存**：维护 `bool storageMayHaveWarper`（`AddItem` 物品 1210 时置位、扫描扑空时清位）比"缓存槽索引"更鲁棒——后者在 storage 压缩/重排（多处）时要同步维护，易漏。

### 不建议

- 不要去掉 `DetermineDispatch` 里的锁（与 `InternalTickRemote` 并发访问 storage）
- 不要改 10/30/60 的 period 大小（玩家可见的调度反应速度）

## 六、BuildToolOpt 对比

来源：`DSP_Mod/BuildToolOpt/src/Optimization/DispatchOptimize_Patch.cs`
默认 `EnableDispatchOptimize = false`，需在 cfg 手动开启。

### 它做了

| # | 做法 | 对应我的方案 | 评价 |
|---|---|---|---|
| 1 | **Early-exit on `DetermineDispatch`**：Prefix 判断 `idleShipCount==0 \|\| energy<=6e6` 直接 `return false` | 未在我的清单 | ✅ **漏网的好点子**，几乎零代价，直接消除上文 §3 的"空转扫 pair 环"浪费 |
| 2 | **Stagger priorities**：改 `DetermineFramingDispatchTime`，让 p1..p6 分别落在 `t%10==0 / %30==10 / %30==20 / %60==15/45/55`，不再重叠于 `t%60==0` | 部分 P0 | ⚠️ 只削掉了"priority 之间同帧重叠"，**同一 priority 内 10000 塔仍然同帧**，每个 priority 自己的 N-spike 还在 |
| 3 | **Amortize into chunks**：`GameTick` 整段 Prefix，把塔按 `AmortizeChunks=5` 分组，每次触发只处理 1/5 | 变体 P0 | ⚠️ 确实把 priority 内 spike 再削到 N/5，**代价：每塔的调度频率从 10/30/60 tick 变成 50/150/300 tick（×5）**，调度响应变慢 |

### 它没做

| 我的方案 | BuildToolOpt | 差距 |
|---|---|---|
| P0 gid 相位分散（保频率） | ✗ | 用 chunk 代替，代价是调度延迟 ×5 |
| P1 ① warper 槽缓存 | ✗ | `InternalTickRemote` 每 tick 仍 `lock(storage)` 扫 30-50 槽 |
| P1 ② `pair.trip` 缓存 | ✗ | `DetermineDispatch:3008` 仍每对重算 magnitude |
| P1 ③ planet-pair 距离表 | ✗ | `InternalTickRemote:1779` 每船每 tick 仍 Sqrt |
| P2 活跃塔列表 | ✗ | chunk 遍历仍是稀疏 `for + 三重判空` |
| P3 `Array.Copy` → swap-last | ✗ | `1824-1825` 未动 |

### ②/③ 的语义注意点

- **Early-exit** 会**彻底**跳过原方法 → `other.SetPriorityLock(...)`（行 3036/3050）也不执行；`remotePairProcesses[priority]` 游标不推进；`_tmp_iter_remote` 不变。挂机体感没问题，但不是零语义。
- **Chunk** 会把每塔被访问的间隔拉长 ×chunks，意味着 priority=1 的高优先级调度从每 10 tick 一次退化到每 50 tick 一次。

## 七、落地建议

做"比 BuildToolOpt 更优"的挂机补丁，推荐顺序：

1. **吸收 BuildToolOpt 的 early-exit**（§6.1 #1）— Harmony Prefix 一行，几乎零风险。
2. **用 P0 gid 相位分散替换 BuildToolOpt 的 stagger+chunk**（§5 P0）— 同样削平 spike，但保持原调度频率。
3. **P1 ① warper 槽索引**（§5 P1①）— 每 tick 10 万级字段比较归零。
4. **P1 ② `SupplyDemandPair.trip` 缓存**（§5 P1②）— 稳态 `DetermineDispatch` Sqrt/magnitude 减掉。
5. 余力：P2 活跃塔列表、P3 飞船到达 swap-last。
6. **若 1–5 仍不够 → P4 事件/脏标记驱动**（§5 P4）— 收益上限最高，但要充分回归测试，作为压轴而非首发。
