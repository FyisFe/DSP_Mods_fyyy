# PoolTrim 后续运行时内存机会：原档离线核验

日期：2026-09-05 UTC（本地 2026-09-04）。本报告记录基于 PoolTrim 1.1.1、当前游戏程序集、900 万糖原档和对应读档日志的离线分析。后续 1.2.0 冷存实验版的实现、验证与限制由 [PoolTrim README](../../../PoolTrim/package/README.md) 维护；本报告的估算不等同于游戏内优化结果。

## 结论与优先级

**最大的方向仍是路径几何，但现在有真实无损压缩样本支持；新增明确的 GiB 级目标是物流塔供需配对表。** 继续给普通池统一加裁剪，并不是这个档的主要突破口。

| 顺序 | 方向 | 本次证据与量级 | 下一步 |
|---|---|---|---|
| 1 | 远端路径几何无损冷存 | 两组样本压至原始的 40.72% / 42.39%；全档同率条件算例减少约 **10.7–11.0 GiB** 几何载荷 | 验证单工厂恢复、连续保存、远端拆建与帧时间 |
| 2 | 物流配对只保留当前模式需要的组 | 原档按原版规则推演约 **2.189 GiB** 数组容量；省去当前不用的普通组后约 **1.094 GiB** | 先核验游戏内配对容量，再验证模式切换、返航带货、成就和 BuildToolOpt |
| 3 | 配对表尾部整理 | 同一配对表约 **0.678 GiB** 空闲容量，零余量上限 | 若选择上项，按最终表重新计算，不能叠加旧尾部收益 |
| 4 | 空间索引容量整理 | 两类索引合计 **0.633 GiB**；外层尾部约 **0.211 GiB**，桶内空闲约 **0.140 GiB** | 次要候选，不作为 GiB 级主线 |

表中压缩外推和配对重建都是离线推演，不是游戏进程已减少的提交量。已有货物 GPU 按需驻留候选仍成立，原档容量对应约 3.02 GiB 逻辑缓冲；其契约与显存口径由[前一份调研](2026-09-04-pooltrim-runtime-memory.md)说明，本轮不重复计为新发现。

## 原档与校验边界

- 原始存档：`900W/Day24-结档.dsv`，46,679,237,264 B。读档日志前缀：`load_Day24-结档_20260904_231421_8850577`。
- 通过 schema 3 时间线的 `file_bytes` 定位原版序列化分段，只读映射文件，跳过不需要的载荷，不创建游戏对象。
- 当前 `Assembly-CSharp.dll` SHA-256 复核为 `AE0BA95F75BD879A62AA4CE253B2AB78EAA4FB3C7C595F5E1FEE75EBE0E0EF85`，与前一轮一致；源码 MVID 为 `ECE4A40E-5E73-43F4-A9F8-4E74970B5942`。
- 全部 266 个工厂的路径头、货物头、空间索引元数据和物流站记录已解析。路径、货物容量和 cursor 与既有完整原档报告一致。
- 路径共 1,231,495 条，有效 714,469,350 点，原保存容量 2,283,073,600 点；货物容量 101,352,448，cursor 59,753,959。不能把 cursor 当作活货物数。
- 空间索引段逐厂严格到达 Entity 起点；物流站段逐厂严格到达 Transport 结束位置。解析器拒绝不匹配的记录版本；这不是支持任意存档的通用解析器。
- 当前日志的 900 万糖运行期容量扫描被取消，不能用其残缺快照充当本轮全量运行期测量。原版配对重建也不代表所有模组加载后的实际数组。

## 1. 路径几何：无损压缩已有实物依据

`CargoPath.Export` 保存每条路径完整的 `Vector3[] pointPos` 和 `Quaternion[] pointRot` 原始 float 字节；三数组裁剪之后，几何仍为每个有效点 28 B，原档总计约 18.631 GiB。

抽样使用完整路径，逐路径独立压缩，避免把跨路径的大字典收益误算为可随机恢复的小块收益。第一组按 `(pathId + factoryIndex × 17) % 521 == 0`，并加入每厂 1 号活路径；第二组将余数平移 137，不额外加入首条路径。两组均覆盖 233 个工厂，路径键交集为零，没有路径触及单样本 8 MiB 上限。

| 方法 | 第一组：2,598 条，82.872 MiB 原始字节 | 第二组：2,365 条，33.271 MiB 原始字节 |
|---|---:|---:|
| zlib level 1 | 66.391 MiB / 80.11% | 26.942 MiB / 80.98% |
| zlib level 6 | 65.782 MiB / 79.38% | 26.752 MiB / 80.41% |
| float 字节重排 + zlib level 1 | 47.878 MiB / 57.77% | 19.500 MiB / 58.61% |
| 同分量整数差分 + 字节重排 + zlib level 1 | **33.742 MiB / 40.72%** | **14.104 MiB / 42.39%** |

“整数差分”将 float 当作原始 uint32 位模式，对相邻点的同一坐标或四元数分量作模 2³² 减法；首点保持原位模式。随后把每个 32 位值的四个字节按字节位置分组。恢复使用模 2³² 累加和逆重排，没有 float 舍入、插值或几何重建。离线实验使用 Python、已安装的 NumPy 和标准库 zlib。

全部 4,963 条样本的四种处理均解压并逐字节与原数组比较，通过。样本合计 121,785,300 B，约为全档有效几何字节的 0.61%；两组不是随机抽样置信区间，不能保证其他存档或所有路径有相同比例。

条件算例：若全档有效几何都达到这两组差分压缩比例，原始 18.631 GiB 与压缩载荷之差约为 **10.733–11.045 GiB**。实际净收益还需扣除本地热路径、压缩块及索引开销、临时恢复缓冲；也可能因运行时编解码器不同而变化。第一组额外包含首条路径，原始字节较多，单独报告两组以显示抽样差异。

没有用 Python 编解码耗时预测 Mono 中的落地耗时或自动保存耗时。下一阶段只需一个有界原型，验证完整工厂恢复、原版格式逐路径保存、保存失败后的状态、远端战损及退出换档。绘制、编辑、导出和销毁的访问边界仍按[已有冷存契约](2026-09-04-pooltrim-runtime-memory.md#3-远端传送带几何无损冷存)逐一覆盖；不能只把两个数组置 null。

源码依据：`CargoPath.cs:67–143`、`CargoTraffic.cs:2467`、`GameLogic.cs:1036`。此次只验证序列化几何的可逆压缩，不验证游戏内补丁。

## 2. 新目标：物流配对表的重复组与尾部

### 为什么前一轮没有看见

`StationComponent.Import` 导入塔库存、物流机和设置；全局 `GameData.Import` 在所有工厂导入后调用 `GalacticTransport.RefreshTraffic`，再进入 DysonSphere 分段。配对表是此时构造的运行数据，不能用 Transport 序列化分段的增量给它定上限。

现有 LoadMemProfiler 容量扫描没有遍历 `StationComponent.localPairs/remotePairs`。下一次应只读取数组长度和六组边界，不逐条扫描数千万个配对。

### 原档推演

解析得到 30,056 座物流站，其中 26,282 座拥有全局 gid。所有这些星际站均为 `Prioritize`，分组 mask 全为 0；存档包含 825 条启用的星体路线、0 条塔间指定路线、0 条禁运记录。计算按物品、供需角色和行星分组，排除同星球供需配对，检查行星/恒星路线，避免真的创建笛卡尔积数组。

`SupplyDemandPair` 有五个 int，载荷 20 B。一次匹配会在供给站和需求站各保存记录；未指定路线时，每一端同时写普通组和兜底组。存在路线时按相应优先级写组。它们承担不同调度策略，不能仅按四个端点字段相同就全部去重。

| 指标 | 原版重建推演 |
|---|---:|
| 普通供需关系数 | 20,273,823 |
| 两端及各组实际记录总数 | 81,095,292 |
| 所有站逐个从 128 起步翻倍后的容量合计 | 117,508,224 条 |
| 有效记录载荷 | 1.5105 GiB |
| 容量载荷 | **2.1888 GiB** |
| 尾部空闲载荷 | 0.6782 GiB |

这个存档没有同时命中多级路线而增加第三份组记录的匹配，记录总数等于供需关系数的四倍。不能把此倍数推广到所有存档。

### 可行的收缩边界

`GalacticTransport.GameTick` 对 `Prioritize` 调度组 1–5，普通组 0 用于 `Ignore`；`StationComponent.InternalTickRemote` 的返航带货也按当前模式选组。当前档所有星际塔均为 `Prioritize`，因此普通组 0 的 40,547,646 条记录不参与当前模式的发船和返程选货。

如果这些记录不被物化，且继续采用原版 128 起步、按需翻倍，容量推演降到 58,754,304 条，即 1.0944 GiB，减少 **1.0944 GiB**。更简单的“只裁最终尾部”零余量上限是 0.6782 GiB；两种收益有重叠，不能相加。

这需要维护原有逻辑计数和重建边界，不是一个无条件删除组的 postfix：

- `remotePairTotalCount` 实际返回 `remotePairOffsets[1]`，即普通组数量；全局计数和物流成就依赖它。取消普通组的实物记录后仍须保留原有计数语义。
- UI 修改模式会调用 `RefreshTraffic`；粘贴设置、路线和禁运变更、远程编辑及模组直接赋值也要核对。进入 `Ignore` 前必须已有所需记录，不能以缺组改变物流行为。
- 已安装的 BuildToolOpt 处理单塔变动时增删配对，读取全部组并比较两端记录数量。不同模式的塔若保留不同组数，可能破坏它对数量对称的假设；本轮只阅读了本地源码，没有完成安装 DLL 的补丁组合验证。
- 保留组内顺序、各组偏移、扫描位置、优先锁和在途订单；返程带货不能遗漏。更激进的共享配对图或改成按物品即时查找会扩大调度改造面，暂不需要。

源码依据：`StationComponent.cs:90,475–571,761–891,2353–2384,2935–2960`，`GalacticTransport.cs:175–224`，`GameData.cs:794`，`UIStationWindow.cs:1458–1459`，本地 `BuildToolOpt/src/Optimization/GalacticTransport_Patch.cs:225–315`。

## 3. 两个已核验、但不应高估的池

### Cargo CPU 尾部不能照搬实体裁剪

旧报告的 101,352,448 个容量槽与 59,753,959 的 cursor，相差约 1.240 GiB Cargo 结构载荷。但 `AddCargo` 和 `RemoveCargo` 使用 `index & (poolCapacity - 1)` 访问回收环，要求容量为 2 的幂。

本次逐厂计算 `max(1024, nextPowerOfTwo(cursor + 1))`，**266 个工厂全部等于原容量**。在不改变货物 ID、高水位、回收环算法和原版初始容量的前提下，直接缩容收益为零。它与实体池可采用任意正容量的契约不同。

若要取得旧报告的 1.240 GiB，需要更改容量/回收算法，或重排货物 ID 并更新引用；这已经不是廉价的尾部裁剪。GPU 按可见工厂驻留仍是另一个独立机会。

源码依据：`CargoContainer.cs:77–148,195–220,283–335`。本节不声称货物活数恒定，也不把回收孔洞直接截掉。

### 空间索引是亚 GiB 项

原档每个 HashSystem 的 bucketCount 为 362，已用两个连续索引段及全部桶偏移/高水位约束验证。动态和静态两组主要数组载荷合计 679,988,720 B，约 0.6333 GiB。

- `hashPool/hashRecycle` 在最后一个桶之后保留 226,823,424 B，约 0.2112 GiB。
- 桶内部在各自 cursor 之后另有 150,344,096 B，约 0.1400 GiB；回收孔洞没有计入这项。
- 原版 `ExpandBucket` 允许桶容量和总数组长度改变，但零容量桶无法正常翻倍。整理桶必须保留桶内索引、回收序列、正容量和增长余量。

这里未计对象头、线程临时数组及共享静态 bucketMap；后者原版为 32,000,000 个 4 B Cell，只有一份约 122 MiB，不能乘以工厂数。约 0.3513 GiB 是两类空闲相加的零余量上限，不是计划实现的净收益。

源码依据：`HashSystem.cs:31–43,70–97,459–524`。

## 4. 其余上限与暂不投入的方向

- **实体主结构/连接/标志的紧凑表示**仍有数 GiB 量级的数据，但直接访问和序列化契约广泛，不能通过变更结构布局做兼容补丁。连接数组也不是纯冷数据：`PowerGeneratorComponent.cs:380–383` 的接收站输送过程会查询它；远端工厂每次查询都整厂解压会使冷存失效。
- **每台机器的库存小数组、Mutex 对象**不在当前完整容量口径内，但配方不可变数据原版已共享。原版还明确不给皮带、分拣器等创建实体 Mutex；不能把 3,693 万个实体都算成可删除锁对象。没有新的 GiB 级证据，暂不为它们改库存结构或锁粒度。
- **减少读档临时分配**仍可能改善后续堆高水位，例如直接按路径长度分配。已有同进程重读观测支持继续研究，但尚未把具体提交增量归因给某处分配。Unity 2022.3 的 GC 不移动对象来填补碎片，[官方说明](https://docs.unity3d.com/2022.3/Documentation/Manual/performance-incremental-garbage-collection.html)并不提供一次强制 GC 就能等量降低进程提交的保证。

几何冷存实验版仍需游戏内核验恢复成本和进程内存，物流配对则需独立核验实际模组组合下的容量与访问契约。
